# Host-wide health-only cutover fence

This is an opt-in, typed startup mode, not a runtime toggle. Deploy the same reviewed source SHA to **every** backend, worker and consumer host with both `WARMBLY_MAINTENANCE_MODE=health-only` and `WARMBLY_MAINTENANCE_SCOPE=host`. An org scope is deliberately unsupported: shared schedulers, event queues, webhook callbacks and workers cannot be isolated by org at startup. Partial/malformed settings fail startup. With both variables unset, legacy normal startup remains unchanged. `API_HOST` controls the backend listener (default `0.0.0.0:8080`).

1. Before switching any backend route, stop/verify quiescence of **all old** backend, worker and consumer instances, including restart policies/auto-scaling and any other sender binaries; do not trust campaign/warmup pause or a zero NATS pending count. Freeze externally hosted Cloud Tasks queue delivery before routing callbacks to this backend: health-only returns 404, which can exhaust retries and delete tasks if deliveries continue. Record exact task-row states, queue depth/ack counters, process inventories, image digests, source SHA and backups before/after. If an old send-capable process survives, or Cloud Tasks cannot be frozen with a verified readback, STOP; this mode does not fence it.
2. Run `cmd/migrate` independently under an approved migration permit; backend health-only bypasses config/DB initialization and does **not** migrate. Boot the reviewed binaries with both variables, verify each old instance is gone and every new role has the variables. Worker and consumer remain alive without subscribing or acknowledging NATS. Backend serves only `GET/HEAD /health`; all API routes, task webhook, manual/direct sends, campaign/warmup schedulers/reconcilers and placement/test/notification sends are absent. `/health` proves process liveness, **not** DB/mailbox/queue health. No mailbox sync canary is offered in this mode because starting a worker subscription would also risk queued sends. Use an independently reviewed non-sending sync tool if needed.
3. Verify external task rows and queue counters remain unchanged across restart (apart from explicitly accounted pre-quiescence activity). Any unexpected task claim/ack, send, or retry is a hard stop. Keep old services stopped and queue delivery frozen on rollback too; rolling back to an unfenced image or removing the variables restores send-capable startup immediately. A separate reviewed resume, quota, delivery and outcome gate is required before unfreezing queues or starting normal processes. In particular, `internal/tasks/campaign_task.go` cancels a due task when its campaign is paused (`ErrCampaignNotActive`), while resuming a campaign re-seeds work beyond the existing pending rows. Owner approval for 15 pending sends is **not** permission to boot a normal backend or resume all campaigns: preserve and reconcile exact task IDs/statuses first. This health-only stage cannot release those tasks or perform mailbox sync. A future release must separately bind exact recipient/account warnings, configured per-mailbox rate limits, eligibility, idempotency and post-send readback under its own permit.

No production operation is performed by the source patch or its tests. Do not use this mode as a per-org fence, provider connectivity check, mailbox canary, or authorization to resume sending.
