# Outlook ID-preserving reconnect: source-only gate

Status (October 8, 2026): delegated same-identity path implemented and tested against an isolated disposable PostgreSQL schema; not approved for production, operated or deployed. No public HTTP route, scheduled repair or migration exists. The existing path is **not** a repair of the five inactive accounts, the ten shared/delegated token rows, or the separate active-account warning lifecycle. The owner authorized investigation and an eventual Graph API-based repair of all five, plus bounded automatic recovery of future recurrences, on October 8 at 18:11 UTC. That authorizes the goal, **not** a production permit, specific credential replacement, unverified activation or bypass of independent review.

## Existing source-only path

`EmailService.ReconnectOutlook` exchanges a fresh delegated authorization code, reads Graph `/me`, requires its email to match the existing active Outlook account, then compare-and-swaps only the OAuth access token, refresh token and expiry. The transactional repository check binds account ID, user ID, organization ID, mailbox email, provider, active status and previous *decrypted* refresh token, and encrypts replacements. A CAS miss stops; it must never insert a replacement account or fall back to another ID. `/me` proves the signed-in principal for that token, **not** another mailbox's original parent, mailbox-level delegation, or an app-only identity. This method intentionally rejects inactive and app-only rows; do not route them through it. Do not store codes or raw tokens in shell history, files, logs, chat or PRs.

## Exact-ID restricted Graph verification before designing a repair

Use a fresh, read-only, account-specific prestate on the named production host/database, stored in a restricted evidence area. Join each of the **five inactive account IDs** to its existing account, credential kind, user/organization, worker/sender assignments, status and status/error history; derive the original parent from authoritative onboarding/audit/provider evidence, not from a current candidate token or email-string similarity. Record expected tenant and original parent for each exact ID, where evidenced, plus consent state, last known successful Graph operation, inactive cause, and any duplicates or suppressed targets. Classify the app-only fifth separately. If the original parent cannot be proven, label it unknown and stop its relink. No identity labels, bearer tokens or mailbox contents belong in a public artifact.

For each *delegated* candidate, with an appropriately scoped **read-only** Graph token and no credential write:

1. Validate token audience/client, issuer/tenant `tid`, subject/object ID and delegated `scp` against the approved tenant, client and required `Mail.Read.Shared` or other narrowly necessary read scope. Inspect claims privately; a `roles` claim alone is not proof of application-only access. `GET /v1.0/me?$select=id,mail,userPrincipalName` establishes the signed-in parent. Compare its immutable ID and tenant to the original parent evidence, not just email; `mail` can be absent or differ from UPN.
2. Resolve the **exact intended mailbox** with `GET /v1.0/users/{mailbox-id}?$select=id,mail,userPrincipalName` under a permission that permits that lookup. If this call is unauthorized, use an authorized directory/Exchange read-only inventory instead; never infer ID from a folder `200`. Check target mailbox tenant and identity against the approved account and original onboarding/audit record. `GET /v1.0/users/{mailbox-id}/mailFolders/inbox?$select=id` and `/mailFolders/junkemail?$select=id`, or a bounded message metadata read under the approved delegated scope, can establish access to that resource at that time. They do **not** prove the grant's provenance, original parent, lasting consent, ingestion or safe reactivation. A `403`/`404` or tenant mismatch is a hard stop, not a cue to try another identity.
3. Confirm mailbox-level delegation for the **same parent and target** from authoritative Exchange/admin grant readback where Graph cannot expose the grant. Distinguish folder share versus mailbox delegation; a successful Graph folder GET proves effective access at the time but not which grant conferred it. Reconcile the token's delegated scopes and tenant with the application's consent grant and the target's actual grant. If consent is missing/revoked, obtain scoped interactive reenrollment from the legitimate parent only after the exact mapping is independently reviewed. Never copy another account's token or silently replace a shared token.
4. Reconcile the actual inactive reason (auth, policy, abuse, admin action, revoked consent, or other) and sender/campaign/warmup restrictions from exact account-specific error and audit history. An auth success cannot override a policy/admin hold. Record a positive resolution criterion for each ID before proposing a reactivation; no blanket status update.

The **app-only fifth** has no signed-in `/me`, no delegated refresh token and no parent reenrollment path. Separately verify application `appid`/client ID, `tid`, audience and application `roles`/consent, then the exact mailbox's effective app scope through Exchange RBAC for Applications (or the deployment's existing application access policy) and bounded `GET /v1.0/users/{mailbox-id}/mailFolders/{folder-id}` read. Check for unscoped Entra grants that can widen RBAC scope. Confirm its inactive cause independently. An app-only Graph `200` alone does not authorize activation or delegated-token substitution. This is a distinct reviewed implementation and permit lane.

Use only existing authorized Graph/Exchange access, least-privilege metadata responses, bounded calls and restricted raw receipts (HTTP status, tenant, principal and target IDs, request IDs, times, grant source, no token value). A lack of API privilege is an evidence gap requiring an authorized administrator, **not** permission escalation by this task.

## Proposed bounded recurrence recovery, not implemented here

For later source changes, classify a transient transport/429/5xx failure separately from `401`, `403`, invalid/revoked consent, tenant mismatch and policy holds. Bound refresh and retry by attempt count and provider `Retry-After`/backoff with jitter; do not spin on invalid grants. Singleflight or serialize refresh per *account ID*, preserve envelope encryption, and CAS against that account's prior encrypted identity/refresh state. After a CAS miss, reread the **same** ID and reclassify; never overwrite a concurrent valid rotation or silently create/relink another row. Refresh only with a valid grant belonging to the proven principal/tenant and account; shared/delegated recovery must revalidate the original parent and mailbox grant. Unauthorized refresh or missing consent ends in an explicit account-specific `reauthorization_required`/operator gate, never a silent repair. App-only credentials follow a separate scoped client-credential renewal path, with no delegated refresh. Do not auto-reactivate an inactive account, clear warnings, change a worker/campaign/sender, send mail or rewrite cursors on refresh success. Require focused tests for retry cap, `Retry-After`, permanent auth failure, tenant/parent mismatch, CAS races, ciphertext sealing and no cross-account mutation before proposing this for review.

## Production and outcome gates

Before any write, obtain an independent reviewer approval and an immutable account-specific production permit binding exact ID, original principal/tenant/consent and mailbox grant, allowed capability, code/config hashes, target, budget and expiry. Prepare a private prestate receipt, execute **one** bounded approved operation, exact-readback the same account, credential metadata (never secrets), status and sender associations, and reconcile it. If prestate changes, identity differs or a grant is missing, stop. Reenrollment or activation is a separate approved action only after its corresponding evidence and inactive-cause gate. Never treat directory/folder `200` or cursor freshness as sufficient proof.

The active-account warning lane is separate: the October 8 read-only census counted 105 unresolved active `SERVER_UNREACHABLE` warnings, while active inbox/junk cursors advanced. This is **not** authenticated UI warning equivalence or proof of message ingestion. Confirm a successful account-specific Inbox and Junk poll, known-message ingress and no newer failure before expecting the independently deployed PR26 warning lifecycle to clear the corresponding warning. Do not blanket-clear warnings. This PR supplies no production Graph/Exchange grant receipts, token writes, activation, warning clear, deployment or business-outcome proof.
