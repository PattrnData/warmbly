# Existing Outlook shared sender: credential-mode conversion

This is a gated recovery mechanism, not a mailbox creation, activation or send operation. `POST /emails/onboarding/outlook-app-only/convert` (under the existing onboarding route group) accepts `account_id`, `parent_email_account_id`, `email`, and `tenant_id` (UUID). Use only after independent authorization and verification of the exact account IDs, owner, shared-mailbox identity and tenant. The caller must have organization access and manage-emails permission. Never call this route merely because an account is inactive.

Before any production call, collect an access-controlled, encrypted preimage/receipt for the **exact target**: account ID, email, owner/org, provider, status, OAuth row ID/credential ciphertext, and hashes of the relevant rows; separately collect the parent ID, status and OAuth credential hash. Do not copy tokens into logs, tickets or PRs. Confirm the target is the intended shared mailbox, the parent is an active delegate for that tenant and the parent/target sealed refresh credential is an identical copy. Confirm app-only Graph `Mail.ReadWrite` and `Mail.Send` roles and tenant-scoped policy externally. Validate an approved permit/hash and hold all sends and status transitions. A Graph inbox GET alone is not proof of sending or mailbox classification.

The route rechecks owner/org, IDs, address, inactive Outlook status, active delegated parent, same sealed credential provenance, tenant-specific app token URL/claims and Graph inbox access; a single SQL compare-and-swap updates only the target OAuth row to the existing sentinel (`access_token=''`, `refresh_token=graph-app-only`, `expires_at=now()`). Concurrent/repeated or mismatched calls fail closed. The `email_accounts` row, ID, status, histories and parent are unchanged. Do not interpret HTTP 200 as restored send/receive capability.

After an authorized conversion, exact-read back the target and parent by their IDs, count rows and reconcile IDs, status, credential mode, owner/org, provider, target email and parent hash against preimage. Keep the target inactive until separate receive/send verification and release approval. On any mismatch, halt further conversions and sending.

Rollback is a **separate approved operation**, not an HTTP endpoint: restore the encrypted preimage of **only the original target OAuth row** inside a transaction, conditioned on the exact target ID, owner/org, expected inactive status and current app-only sentinel; assert one affected row and independently read back exact-row hashes. Abort on zero/multiple rows, drift, missing preimage or new writes. Never copy the parent's credentials as an ad-hoc rollback. PostgreSQL automatically rolls back a failed single-statement conversion; restoring an already-committed conversion requires the preserved preimage and a new independent gate. No production writes are performed by the tests in this PR.
